# Автоматический учёт новых постов

## Короткий ответ

Да, новые посты можно учитывать автоматически.

Лучший вариант:

- Telegram-бот становится админом канала;
- получает все новые `channel_post` и `edited_channel_post`;
- сразу сохраняет текст поста в память;
- запускает пайплайн: нормализация -> аннотация -> обновление карты тем -> обновление backlog.

Но важно понимать ограничение:

- бот видит только новые посты после подключения;
- старую историю канала он сам не подтянет.

Поэтому оптимальная схема такая:

1. Исторические посты один раз загружаются из экспорта.
2. Все новые посты дальше ловятся автоматически ботом.

## Что именно может Telegram-бот

Если бот добавлен в канал как администратор, он может получать:

- новые посты канала;
- отредактированные посты канала.

Это даёт два полезных сценария:

1. Автосохранение после публикации.
2. Пересохранение, если пост был отредактирован после публикации.

## Главное ограничение Telegram Bot API

Бот не является хорошим инструментом для чтения полной истории канала задним числом.

То есть логика должна быть такой:

- прошлое импортируем отдельно;
- всё новое пишем в память через webhook/update handler.

## Рекомендуемая архитектура

### Вариант A. Лучший

Публикация может происходить как угодно, но бот как админ слушает канал и забирает каждый новый пост.

Поток:

1. Вы публикуете пост в канале.
2. Telegram отправляет боту `channel_post`.
3. Ingest-сервис сохраняет сырой payload.
4. Нормализатор приводит пост к вашей внутренней карточке.
5. Аннотационный слой выставляет:
   - `primary_theme`
   - `content_role`
   - `mentions_ai`
   - `cta_present`
   - черновой `core_thesis`
   - editorial semantic layer:
     - `primary_thesis`
     - `secondary_theses`
     - `angle`
     - `content_goal`
     - `funnel_stage`
     - `business_dimensions`
     - `format_type`
     - `novelty_window_days`
6. Planner memory обновляет:
   - `posts_index`
   - `topic_map`
   - `content_backlog`
   - `current_feed_snapshot`

Плюсы:

- почти без ручной работы;
- ловит даже посты, опубликованные не через интерфейс бота;
- хорошо подходит для долгой эксплуатации.

### Вариант B. Ещё лучше для качества

Публикация идёт через вашего бота или через внутреннюю админку.

Поток:

1. Вы даёте тему или черновик.
2. Planner предлагает лучший угол.
3. Writer пишет 1-3 варианта.
4. Вы выбираете финал.
5. Система публикует сама.
6. Этот же текст сразу записывается в память как опубликованный пост.

Плюсы:

- память всегда совпадает с реально опубликованным текстом;
- легче версионировать черновики и финал;
- проще строить аналитику.

Минус:

- надо делать интерфейс публикации.

### Вариант C. Резервный

Если вы публикуете руками и не хотите сразу подключать admin bot:

- раз в день или раз в неделю запускать синк из нового экспорта;
- находить только новые post_id;
- дописывать их в память.

Это рабочий, но менее удобный путь.

## Что я рекомендую именно вам

На вашем месте я бы сделал гибрид:

1. Сейчас:
   - оставить исторический импорт из `messages.txt`;
   - построить память и planner.
2. Затем:
   - подключить Telegram-бота как админа канала;
   - автоматически слушать новые посты.
3. Позже:
   - добавить публикацию через бота как отдельный режим.

Так вы не блокируете запуск логики, но сразу получаете автопамять на будущее.

## Как хранить новые посты

Минимально нужен `published_posts` store.

Например, в `SQLite` или `Postgres`.

Поля:

```json
{
  "telegram_chat_id": "channel_id",
  "telegram_message_id": 1234,
  "published_at": "2026-03-13T12:00:00+03:00",
  "edited_at": null,
  "text": "Текст поста",
  "media_type": "text|photo|video",
  "source": "telegram_channel_post",
  "status": "published"
}
```

Затем на базе этого формируется уже ваша расширенная карточка для контентной памяти.

Теперь эта карточка должна быть пригодна не только для поиска темы, но и для semantic comparison и content-plan planning.

## Как избежать дублей

Ключ дедупликации:

- `telegram_chat_id`
- `telegram_message_id`

Если пришёл `edited_channel_post`, то запись не создаётся заново, а обновляется.

## Что делать с медиа-постами

У Telegram-поста может быть:

- только текст;
- фото + подпись;
- видео + подпись;
- документ + подпись.

Для памяти канала важнее всего:

- `caption` если она есть;
- `text` если это текстовый пост.

Если подписи нет, такой пост лучше:

- либо пропускать;
- либо хранить как `non_text_post`, но не включать в planner.

## Как встроить в текущий проект

Нужны 4 новых слоя.

### 1. Ingest handler

Сервис, который принимает Telegram updates:

- webhook или long polling;
- фильтрует `channel_post` и `edited_channel_post`;
- пишет сырой update в лог.

### 2. Normalizer

Преобразует update в вашу модель:

- `post_id`
- `date`
- `title_hook`
- `body_text`
- `hashtags`
- `cta_present`
- `mentions_ai`
- мягко добавляет editorial metadata defaults через normalizer

### 3. Annotator

Ставит черновые смысловые поля:

- `primary_theme`
- `secondary_themes`
- `content_role`
- `core_thesis`
- `repeat_risk`
- `primary_thesis`
- `secondary_theses`
- `angle`
- `content_goal`
- `business_dimensions`
- `format_type`
- `novelty_window_days`

### 4. Memory updater

Обновляет:

- `posts_index`
- `posts_index_summary`
- `current_feed_snapshot`
- `topic_map`
- `content_backlog`

## Практический pipeline

```text
Telegram channel
  -> Bot admin receives update
  -> Save raw update
  -> Normalize post
  -> Upsert published_posts
  -> Build content memory card
  -> Run annotator / editorial extractor
  -> Refresh topic map / snapshot
  -> Make post available to planner
```

## Retro-enrichment для исторического архива

Чтобы старые посты тоже стали частью semantic memory, добавлен CLI:

`scripts/enrich_posts_editorial_metadata.py`

Он нужен после первичного исторического импорта, если:

- архив был создан до semantic layer;
- у части карточек нет `primary_thesis`, `angle`, `business_dimensions` и других полей;
- нужно подготовить старую ленту для semantic novelty classification.

Поддержка:

- `--dry-run`
- `--limit`
- `--mode rules-only`
- `--mode hybrid`

## Как учитывать вашу собственную тему

Это отдельный поток и он не конфликтует с автопарсингом.

Должно быть так:

1. Вы пишете боту:
   - тему;
   - тезис;
   - ссылку;
   - голосовое;
   - сырую заметку.
2. Planner смотрит:
   - что было недавно;
   - не будет ли повтора;
   - какой угол сейчас сильнее;
   - нужен ли CTA.
3. После публикации финальный пост автоматически попадает обратно в память канала.

То есть:

- вход идеи может быть ручным;
- учёт опубликованного поста должен быть автоматическим.

## Что лучше не делать

Не стоит строить всё только на периодическом парсинге экспорта, если планируется реальная ежедневная работа.

Это неудобно, потому что:

- экспорт надо делать руками;
- легко потерять правки;
- нет события "пост только что опубликован";
- хуже работает обновление памяти и planner-а.

## Итоговая рекомендация

Лучший путь:

- исторический импорт из экспорта оставить как стартовую миграцию;
- новые посты учитывать через Telegram-бота-админа;
- вашу тему принимать отдельно как input для planner-а;
- опубликованный результат всегда автоматически возвращать в память.

Именно так система будет одновременно:

- помнить прошлое;
- видеть новое;
- принимать ваши идеи;
- не терять реальный опубликованный контент.
